# LibraCore 1.2.0 Operator Notes

## Deployment posture

Treat v1.2.0 as a controlled minor-line deployment. Promote the exact artifact that passed the release gates; do not rebuild production artifacts from a moving branch.

## Database

Run migrations against a disposable or staging database before production. Verify a backup exists before applying migrations. Never modify a released Flyway migration to repair a production database.

## Health

Use liveness to determine whether the application process is functioning and readiness to determine whether the application is ready to serve traffic with its database dependency available. Do not expose additional Actuator endpoints solely for convenience.

## Configuration

Review CORS origins, session TTL, bootstrap administrator configuration, database credentials, mail settings, reverse-proxy limits, and TLS configuration before deployment. Production secrets must come from the deployment secret store rather than repository files.

## Logs and privacy

Logs should contain operational context without member passwords, bearer tokens, full credential material, or unnecessary personal data. Correlation identifiers may be used to connect a client error to server-side diagnostics.

## Recovery

If deployment validation fails, return traffic to the previously validated release artifact and follow the backup/restore procedure if a database recovery is required. Preserve the failed artifact and verification evidence for investigation.

## Post-deployment smoke

1. Check liveness.
2. Check readiness.
3. Sign in with a controlled test account.
4. Verify catalog read access.
5. Verify a member workflow.
6. Verify circulation workflow in a controlled record set.
7. Verify reservation state handling.
8. Verify reporting access for an authorized staff role.
9. Verify that a member cannot access staff-only routes or APIs.
10. Confirm no sensitive data appears in logs.
