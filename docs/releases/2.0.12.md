# LibraCore 2.0.12 Release Candidate

**Prepared:** 2026-08-19  
**Hardening refreshed:** 2026-08-20  
**Target tag:** `v2.0.12`  
**Status:** frontend dependency closure complete; final CI/recovery/manual/branch-protection gates remain before tagging.

## Version identity

- Backend Maven version: `2.0.12`
- Frontend npm version: `2.0.12`
- Frontend Settings version: injected from `frontend/package.json` at build time
- Version guard: `node scripts/check-version.mjs 2.0.12`
- npm lockfile: committed at `frontend/package-lock.json`, generated by the hosted Node/npm bootstrap

## Product scope

2.0.12 contains the completed LibraCore library-management implementation across cataloging, physical copies, members, accounts, role-based security, issue/return/renewal, reservations/waitlists, fines, circulation policy, reporting/audit, CSV exchange, notifications, staff-account administration, responsive web UI, themes, accessibility-oriented behavior, backup/restore tooling, CI/security automation, and project documentation.

## Release-hardening changes in 2.0.12

- synchronized backend/frontend executable versions;
- removed the hard-coded web version from Settings;
- added build-time frontend version injection;
- added a cross-manifest version validation script;
- added GitHub Actions version synchronization enforcement;
- made backend CI packaged-JAR startup independent of the Maven version filename;
- made release packaging independent of a historical backend JAR filename;
- made the release workflow verify tag/manifest version agreement before expensive build work;
- made the release workflow require `frontend/package-lock.json` and reproducible `npm ci`;
- made the release workflow start the packaged backend JAR and require a healthy `/actuator/health` response against PostgreSQL before publication;
- made normal frontend CI read-only and lockfile-based;
- added an explicit maintainer-only Frontend Lockfile Bootstrap workflow;
- fixed the bootstrap's first-lockfile detection so an untracked `frontend/package-lock.json` is recognized;
- preserve generated lockfile artifacts even when a later frontend check fails;
- fixed the strict `exactOptionalPropertyTypes` API-client defect exposed by the hosted bootstrap and added regression coverage;
- successfully completed hosted lockfile generation, `npm ci`, lint, strict typecheck, deterministic tests, and production build;
- committed the real npm-generated lockfile in `89d1c833` (`build: lock frontend dependencies for 2.0.12`);
- added stale-run cancellation/concurrency controls to Backend CI, Frontend CI, Version Sync, CodeQL, Dependency Review, and the lockfile bootstrap;
- upgraded supported GitHub Actions runtime lines to `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`, `actions/dependency-review-action@v5`, and `softprops/action-gh-release@v3` where applicable;
- retained `actions/setup-java@v5` as the stable Java setup line and `github/codeql-action@v4` for CodeQL;
- disabled persisted checkout credentials in read-only verification/release checkout paths;
- added `.github/CODEOWNERS` for repository-wide and security/release-sensitive ownership;
- added `.github/workflows/recovery-drill.yml` to verify packaged migrations/startup, logical backup/checksum/restore, restored schema/data, and packaged backend health against a disposable restored PostgreSQL database;
- deferred TypeScript 7 and Node 26 type-definition major upgrades from the 2.0.12 stabilization line.

## Verification evidence gathered during hardening

The Frontend Lockfile Bootstrap run first exposed two strict TypeScript errors in `frontend/src/api.ts` after successfully generating the lockfile and completing `npm ci`. Those errors were fixed without weakening strict compiler settings. The rerun then completed every substantive frontend step successfully: lockfile generation, reproducible installation, lint, strict typecheck, tests, production build, artifact upload, and lockfile commit. Its workflow record was later superseded/cancelled by concurrency after those successful steps, but the generated lockfile commit `89d1c833` and step conclusions provide concrete evidence of the successful frontend closure.

A temporary same-repository probe also demonstrated successful CodeQL analysis for both Java/Kotlin and JavaScript/TypeScript earlier in the hardening sequence. Final CodeQL evidence is still being gathered on the current consolidated release-verification source.

Draft PR #11 (`ci: verify 2.0.12 release candidate`) is the disposable current verification harness. It is configured to exercise Backend CI, Frontend CI, Version Sync, CodeQL, Dependency Review, and Recovery Drill and must not be merged.

## Dependency update policy during stabilization

GitHub Actions major-runtime upgrades required for the current hosted environment were absorbed into the hardened workflows and their superseded Dependabot PRs were closed.

Frontend toolchain churn is deliberately separated from release closure:

- TypeScript 7 major update: deferred and PR #5 closed;
- `@types/node` 26 major update: deferred and PR #7 closed;
- Vitest `4.1.7` → `4.1.10` patch PR #6 may be evaluated after the current release verification is green.

`.github/dependabot.yml` now suppresses recreation of the deferred TypeScript and Node-type major lines while continuing normal non-major dependency update discovery.

## Release command after all gates pass

```bash
git tag -a v2.0.12 -m "LibraCore v2.0.12"
git push origin v2.0.12
```

The tag push invokes `.github/workflows/release.yml`. The workflow must be the artifact source of truth for the GitHub release.

## Known pre-tag blockers at latest review

The frontend lockfile blocker is **closed**. The remaining blockers are evidence/enforcement gates rather than missing dependency state:

- the current six-check verification matrix still needs observed successful conclusions;
- role-based browser smoke and manual accessibility evidence remain outstanding;
- `main` branch protection remains disabled in observable GitHub branch metadata and must be enabled after stable check names are confirmed.

Do not publish `v2.0.12` while any of those gates remain open.

## Upgrade/database notes

The current database history consists of Flyway migrations V1 through V6. Never edit an already-applied migration to retrofit a release. Review database backup/restore and rollback implications before deployment; application rollback does not automatically reverse database changes.
