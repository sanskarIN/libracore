# LibraCore v1.1.3

## 🎉 LibraCore v1.1.3 — Maintenance Release

LibraCore `v1.1.3` is the next maintenance release following the published `v1.1.2` baseline.

This release line focuses on **release-state accuracy, synchronized application metadata, reproducible dependency state, and disciplined verification before publication**.

> **Release status:** Release preparation
> **Release line:** `1.1.x`
> **Previous release:** `v1.1.2`
> **License:** MIT

## ✨ Highlights

- Advanced the backend Maven project version to `1.1.3`.
- Advanced the frontend npm package version to `1.1.3`.
- Keep the generated frontend lockfile synchronized with the frontend manifest through the supported npm workflow.
- Continue enforcing backend, frontend, and lockfile version agreement before release tagging.
- Open the next focused maintenance line without rewriting any published release history.
- Keep repository-managed release notes and tag-scoped release automation as the canonical publication path.

---

## 🏗️ Engineering focus

### Version consistency

The intended stable progression is:

```text
v1.0.0 → v1.1.0 → v1.1.1 → v1.1.2 → v1.1.3 → v1.2.0 → ...
```

Before tagging, these values must agree:

- `backend/pom.xml` project version
- `frontend/package.json` version
- `frontend/package-lock.json` root version
- release tag
- release documentation

The executable guard is:

```bash
node scripts/check-version.mjs 1.1.3
```

---

## 📦 Dependency metadata

`frontend/package-lock.json` remains generated dependency metadata. It must be synchronized by the repository's supported npm workflow and reviewed together with `frontend/package.json`.

Do not hand-edit or synthesize lockfile contents merely to satisfy a version check.

---

## ⚙️ CI/CD and release verification

The release remains fail-closed around:

- version synchronization;
- backend compilation and tests;
- PostgreSQL-backed packaged backend startup;
- `/actuator/health` verification;
- reproducible frontend installation;
- frontend linting, type checking, tests, and production build;
- CodeQL and dependency/security analysis;
- database migration validation;
- Recovery Drill and backup/restore verification;
- release artifact generation;
- SHA-256 checksum generation.

A release must not be described as fully verified until its current tag/source has successful release-blocking evidence.

## 🧪 Verification checklist

Before publishing `v1.1.3`:

- [ ] Frontend lockfile is regenerated and committed.

## 🔄 Upgrade from v1.1.2

1. Pull the `v1.1.3` source or release tag.
2. Review the changelog and release documentation.
3. Verify deployment configuration and environment prerequisites.
4. Confirm frontend dependencies using the committed lockfile.
5. Apply pending database migrations through the normal deployment process.
6. Run the relevant verification suite.
7. Back up an existing production database before deployment.
8. Deploy and perform post-deployment health checks.
