# LibraCore v1.1.5 — Operational Observability & Diagnostics

LibraCore `v1.1.5` improves operational visibility without expanding the public diagnostic surface into sensitive application configuration.

## Highlights

- Adds Spring Boot build metadata to packaged backend artifacts.
- Makes the existing `/actuator/info` endpoint report build metadata for deployment identification.
- Keeps health details hidden from the public actuator response.
- Explicitly disables environment and Git metadata contributors so secrets, environment values, and repository internals are not exposed through `/actuator/info`.
- Keeps actuator web exposure limited to `health` and `info`.
- Advances backend and frontend versions to `1.1.5`.
- Preserves the committed frontend lockfile synchronization policy.
- Continues fail-closed release validation and immutable release history.

## Operational diagnostics

The packaged backend now generates Spring Boot build information containing application coordinates and the release version. Operators can use `/actuator/info` to distinguish deployed application versions while the configuration deliberately avoids exposing environment properties, credentials, datasource settings, or Git repository metadata.

The health endpoint remains configured with `show-details: never`, and the actuator web surface remains restricted to `health,info`.

## Verification requirements

Before publishing `v1.1.5`, the exact final source must pass:

1. `node scripts/check-version.mjs 1.1.5`.
2. Backend CI.
3. Frontend CI.
4. Version Sync.
5. CodeQL.
6. Dependency Review/security checks.
7. Recovery Drill.
8. Performance Fixture CI.
9. Backend packaged-artifact verification.
10. Frontend production build verification.
11. Role-based browser smoke testing.
12. Accessibility review.
13. Repository configuration and tracked-secret review.
14. Release artifact and SHA-256 checksum verification.
15. The tag-scoped release workflow.

The `v1.1.5` tag must point to the exact final commit that passed the release-blocking validation.

## Upgrade

1. Back up the production database before deployment.
2. Review deployment configuration.
3. Deploy matching backend and frontend `v1.1.5` artifacts.
4. Apply required database migrations through the normal deployment process.
5. Verify `/actuator/health`.
6. Verify `/actuator/info` reports the expected build version without exposing sensitive environment information.
7. Run relevant role-based smoke checks.
8. Monitor the deployment after release.

## Rollback

If deployment validation fails:

- Stop or disable the new deployment.
- Restore the previous verified `v1.1.x` artifacts.
- Restore the database from the appropriate backup when required.
- Re-run health and smoke verification.
- Do not delete, rewrite, or force-move previous release tags.
