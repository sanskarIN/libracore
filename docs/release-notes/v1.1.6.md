# LibraCore v1.1.6 — Performance & Deployment Validation

## Highlights

- Advances the backend and frontend release line to `1.1.6`.
- Adds explicit Spring Boot liveness and readiness probe configuration.
- Keeps readiness tied to the database health component for deployment safety.
- Adds repeatable latency thresholds over the existing isolated PostgreSQL performance fixture.
- Keeps performance writes gated to the dedicated benchmark database convention.
- Adds deployment-oriented verification guidance without exposing secrets.
- Preserves the restricted Actuator surface and non-sensitive build metadata introduced in v1.1.5.

## Performance Validation

The release adds a deterministic performance-threshold check for representative catalog, circulation, and reservation queries.

The benchmark runs against a dedicated `_perf` or `_benchmark` PostgreSQL database and defaults to a maximum query execution time of 250 ms per representative query.

The fixture remains synthetic and uses the existing explicit write gate. Production databases must never be used for this benchmark workflow.

## Startup and Readiness

The backend now exposes Spring Boot health probe groups for:

- `liveness` — application liveness state;
- `readiness` — readiness state plus database health.

Health details remain hidden, while environment and Git metadata remain disabled. The existing `health,info` Actuator exposure is preserved.

Before publishing the release, verify:

- Version consistency across backend, frontend, and lockfile.
- Backend CI.
- Frontend CI.
- Version Sync.
- CodeQL.
- Dependency Review/security checks.
- Recovery Drill.
- Performance Fixture CI.
- Performance Thresholds CI.
- Packaged backend verification.
- Safe Actuator information output.
- Liveness and readiness endpoint behavior.
- Browser smoke tests.
- Accessibility checks.
- Tracked-secret review.
- Artifact and checksum verification.
- Tag-scoped release workflow.

## Deployment Validation

Recommended deployment sequence:

1. Build the exact release artifact from the verified release commit.
2. Confirm required runtime configuration is supplied through environment-specific configuration or secret management.
3. Deploy the artifact to a non-production environment.
4. Wait for the readiness probe to become healthy.
5. Run smoke checks against the application.
6. Promote only after application, database, and readiness checks succeed.
7. Keep the previous stable release available for rollback.

No secret values should be committed to the repository or printed by deployment verification.

## Rollback

If the release fails operational validation, roll back to `v1.1.5` without rewriting the `v1.1.6` tag or release history.

## Compatibility

v1.1.6 is intended as a backward-compatible reliability and deployment-validation release within the LibraCore 1.1.x line.
