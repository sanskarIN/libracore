# LibraCore v1.2.0 — Platform Maturity & Operational Contracts

LibraCore v1.2.0 begins the next minor release line after the 1.1.x maintenance series. The release focuses on turning the existing library-management foundation into a more explicit, contract-driven platform for future application features.

## Release theme

**Platform maturity without sacrificing operational safety.**

The 1.2.0 line formalizes API compatibility expectations, release contracts, observability boundaries, and contributor-facing verification so that future catalog, circulation, member, and reporting capabilities can evolve without weakening the existing security and recovery model.

## Planned/implemented release-line objectives

- Advance backend and frontend executable versions to `1.2.0`.
- Keep the frontend lockfile root metadata synchronized with the executable manifest.
- Establish an explicit API compatibility policy for the `/api` surface.
- Document stable, additive, and breaking API-change categories.
- Define a release-contract checklist that is reusable by later 1.2.x releases.
- Preserve restricted Actuator exposure and privacy-conscious diagnostics.
- Keep database migrations forward-only and rollback expectations explicit.
- Strengthen release documentation around artifact provenance and verification.
- Keep security, accessibility, performance, and recovery validation as release gates.

## Compatibility policy

The 1.2.x series is intended to remain source-compatible with existing deployment configuration unless a release note explicitly identifies a required migration. API changes should prefer additive fields and endpoints. Breaking changes require an explicit migration note and a versioning decision before publication.

## Operational invariants

- Actuator exposure remains limited to `health` and `info`.
- Health details remain hidden from ordinary responses.
- Environment and Git metadata remain disabled unless intentionally exposed through a reviewed configuration change.
- Liveness remains application-state based.
- Readiness remains database-aware.
- Performance fixtures remain isolated from production databases.
- Sensitive credentials and member data must not enter logs, fixtures, or committed examples.
- Published release tags must never be force-moved or rewritten.

## Verification gates

Before publishing `v1.2.0`, verify:

1. backend and frontend manifests report `1.2.0`;
2. the committed frontend lockfile reports `1.2.0` at its root and workspace package entry;
3. version guards pass;
4. Backend CI passes;
5. Frontend CI passes;
6. Version Sync passes;
7. CodeQL and dependency/security checks pass;
8. Recovery Drill passes;
9. Performance Fixture CI and Performance Thresholds CI pass;
10. packaged startup, liveness, readiness, and build metadata checks pass;
11. browser smoke and accessibility validation pass;
12. deployment configuration and tracked-secret review pass;
13. artifact and checksum review passes;
14. the final tag points to the exact verified commit;
15. tag-scoped validation succeeds.

## Upgrade guidance

Deploy the exact published artifact for `v1.2.0`. Run the application's normal startup and readiness checks, validate database migrations against a backup or disposable environment first, and perform representative catalog, member, circulation, reservation, reporting, and authentication smoke journeys.

## Rollback

Rollback must use a previously validated release artifact. Do not rewrite the `v1.2.0` tag. Database rollback must follow the documented migration and backup/restore procedure rather than editing released migrations.
