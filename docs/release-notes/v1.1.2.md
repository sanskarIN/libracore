# LibraCore v1.1.2

## 🎉 LibraCore v1.1.2 — Maintenance Release

LibraCore `v1.1.2` is the next maintenance release following the published `v1.1.1` baseline.

This release line focuses on **release metadata correctness, documentation consistency, reproducible dependency state, and continued CI/release reliability**.

> **Release status:** Release preparation  
> **Release line:** `1.1.x`  
> **Previous release:** `v1.1.1`  
> **License:** MIT

- Advanced the backend Maven project version to `1.1.2`.

- Correct release-facing documentation so `v1.1.1` is clearly identified as published and `v1.1.2` as the next maintenance target.

---

## 🏗️ Engineering focus

### Version consistency

The intended stable progression is:

```text
v1.0.0 → v1.1.0 → v1.1.1 → v1.1.2 → v1.2.0 → ...
```

The following values must remain synchronized before tagging:

- `backend/pom.xml` project version
- `frontend/package.json` version
- `frontend/package-lock.json` root version
- tag name
- release documentation

The executable guard is:

```bash
node scripts/check-version.mjs 1.1.2
```

---

## 📦 Dependency metadata

`frontend/package-lock.json` is generated dependency metadata and must be produced by the supported npm toolchain. It must not be manually synthesized to make a release appear consistent.

The release source must contain a committed lockfile whose root metadata agrees with `frontend/package.json`.

---

## ⚙️ CI/CD and release verification

The release process remains fail-closed around the following checks:

- version consistency;
- backend compilation and tests;
- PostgreSQL-backed packaged backend startup;
- `/actuator/health` verification;
- reproducible frontend installation;
- frontend lint, type checking, tests, and production build;
- security/dependency analysis;
- database migration validation;
- Recovery Drill and backup/restore verification;
- release artifact generation;
- SHA-256 checksum generation.

A release must not be described as fully verified until the corresponding GitHub Actions runs report successful conclusions.

## 🧪 Verification checklist

Before publishing `v1.1.2`:

- [ ] Frontend lockfile is regenerated and committed.
- [ ] `node scripts/check-version.mjs 1.1.2` passes.
- [ ] Backend CI passes on the final source.
- [ ] Frontend CI passes on the final source.
- [ ] Version Sync passes on the final source.
- [ ] CodeQL passes on the final source.
- [ ] Dependency/security checks pass.
- [ ] Recovery Drill passes on the final source.
- [ ] Role-based browser smoke journeys are reviewed.
- [ ] Accessibility review is completed.
- [ ] Repository links and configuration are reviewed.
- [ ] No secrets or private data are tracked.
- [ ] The final release commit is identified.
- [ ] `v1.1.2` points to that exact verified commit.
- [ ] The tag-scoped release workflow completes successfully.
- [ ] Generated artifacts and checksums are reviewed.

## 🔄 Upgrade from v1.1.1

1. Pull the `v1.1.2` source or release tag.
2. Review the changelog and release documentation.
3. Verify the deployment environment and configuration.
4. Confirm frontend dependencies with the committed lockfile.
5. Apply pending database migrations through the normal application process.
6. Run the relevant test and verification suite.
7. Back up an existing production database before deployment.
8. Deploy and perform post-deployment health checks.
